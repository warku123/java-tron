# Serving Index 尾页与目录写放大：问题分析与优化方向

状态：轻量优化已实施（尾页零解码追加、定长描述符目录、段锚点查询，
全部对齐 Geth）；剩余的物化滞后方向记为待办，先基准后决策。
实现基线 `8ce58a031f65a08a9ab9577ab4b4ee7a7bfb5b5e`，
差分页与页目录的实现说明见 `serving-index-compressed-pages.md`。

## 原问题是什么

最初的实现里，尾页未满时每次追加都要读取尾页、完整解码为 `long[]`、
与新高度合并、整页重新差分编码后写回；页目录用变长差分编码整条重写。
按 commit 次计的写放大：尾页约 533B（512 条连续高度夹具）至约 4.6KB（最坏），
目录 O(页数)；CPU 侧每次追加全页解码＋全页重编码，与新增高度数量无关。
批量增量计划可摊薄，极热 key＋高频小块 SOLO 是主要痛点场景。

## 与 Geth 的对照（优化后现状）

对照基准：go-ethereum `triedb/pathdb`（提交 `6f6a07e6f86b`）。
Geth 落盘同样是整块 value 写回（KV put 语义相同），它省的是解码/重编码 CPU
与落盘频率。本次对齐后：

| 层面 | 我们（对齐后） | Geth |
| --- | --- | --- |
| 磁盘 put | 整条 value 重写 | 整条 value 重写（量级相同） |
| 读后解码 | 零解码，旧编码前缀原样复用 | 零解码，切片引用 |
| 重编码 | 只编码新增字节，段满加 restart 锚点 | 只编码新增字节 |
| 差值基准 | KeyMeta.lastEpoch（原子组保证） | 内存 desc.max |
| 目录/描述符 | 定长 14B/页（max+entries+id） | 定长 14B/块（max+entries+id） |
| 页内查询 | 段锚点二分＋只扫目标段 | 同（seekGT） |
| 落盘频率 | 每次 commit（与进度原子发布） | 内存攒批后落盘 |
| 内存数据丢失 | 不允许，R-IDEM 重放保证 | 允许，后台从 History 重建索引 |

仍不对齐的两项属于状态机而非存储格式：我们的页＋目录＋KeyMeta＋coverage＋
descriptor 同批原子发布、索引进度即发布进度；崩溃恢复用重放收敛而非物理裁剪。
这是既有崩溃语义的取舍，不随块格式对齐而改变。

追加路径因此不再每-commit 校验"尾页内容 vs KeyMeta"（旧实现是解码的副产品，
Geth 从来没有这项）；防御由应用层 CRC、页头条数比对、查询边界校验与
统计扫描承担。目录仍整条写回（value 不可变＋CRC），但定长描述符复制
无变长重算，极热 key 的目录体积（14B×页数）与写回是剩余的线性成本。

## 剩余方向：物化滞后（待办，未实施）

若基准显示目录整条写回或落盘频率仍是热点，候选方向是"物化滞后"：
每个 key 至多一条尾增量记录（差分 Uvarint＋CRC），追加先合并进增量记录；
低于阈值时只写增量与 KeyMeta（同一原子组），达到阈值或跨过页边界才
物化整页、清理增量并更新目录。查询读取最后一页时需要合并增量记录；
崩溃恢复沿用 R-IDEM，不改变重放语义。

属于格式扩展：需新增记录前缀与尾增量编解码，并调整目录末项校验
（末项为物化最大高度，需新增与 KeyMeta.last 的一致性不变量）、
统计扫描、重放校验与预算路径。如果实际负载里热 key 的追加大多随大批量
plan 走，重写早已摊薄，这项优化可以不做。

## 实施前提：先基准后决策

1. 热 key 追加频率分布与 SOLO 高频小块的实际占比；
2. 追加路径分段计时（get/拼接/CRC/put），确认零解码追加的实际收益；
3. 不同阈值下的整页物化频率、增量记录大小与查询尾页延迟对照；
4. 目录整条重写在多页 key 上的字节量与 compaction 影响；
5. 与 Geth 同数据量的写放大对照（同口径统计 put 字节量与 CPU）。
